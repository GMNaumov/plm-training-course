# J04. Разбор разности BOM

[К заданию](../exercises/j04-java-diff/README.md) · [К эталонам](README.md) · [Исходник](java/BomDiff.java)

После reset: `docker compose run --rm java practice/solutions/java/BomDiff.java OLD NEW`. Две строки: o30 REVISION; o50/e20 LOCAL_QUANTITY,ROOT_QUANTITY. CHANGED_PATHS=2. OLD OLD даёт ноль; несуществующий снимок — ошибку.

Оба набора загружаются как Map полного пути в одном согласованном чтении. Объединение ключей позволяет явно показать ADDED и REMOVED. Для общего ключа сравниваются все измерения: родитель/child_item, выбранная ревизия, единица, локальное и корневое количества. Числа сравниваются compareTo: представления 2.0 и 2.00 не создают ложную дельту.

Ревизия и количество — разные категории; изменение родительского множителя может изменить root_quantity при неизменном local_quantity. Смена единицы не трактуется как числовая дельта в общей размерности: требуется UNIT_REVIEW. Авторизация изменения и инженерная совместимость за пределами diff.

Два пути с компенсирующимися количествами не исчезнут из отчёта, даже если агрегированный итог одинаков. Перенос узла на новый путь даст удаление и добавление. Сопоставить такой перенос с прежним вхождением может дополнительное правило идентичности; одинаковый child_item или хеш поддерева не всегда достаточен.

Эталон не выполняет merge и не изменяет OLD/NEW. Трёхсторонняя EBOM/MBOM-сверка из дополнительного исследования остаётся отдельной реализацией: ей нужны исходная база, сохранённые технологические решения и правила разрешения конфликтов. Двусторонний diff не заменяет этот контекст.
