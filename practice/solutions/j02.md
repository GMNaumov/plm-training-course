# J02. Разбор разрешения ревизий

[К заданию](../exercises/j02-java-resolution/README.md) · [К эталонам](README.md) · [Исходник](java/RevisionResolver.java)

После reset: `docker compose run --rm java practice/solutions/java/RevisionResolver.java SEN 2026-07-01 DM 100` возвращает RESOLVED с SEN-B. Для HO с тем же контекстом — HO-A, с номером 101 — HO-B. OTHER даёт UNRESOLVED. Неизвестное изделие даёт MISSING_ROW.

SQL сначала отбирает допущенные released-ревизии. Даты полуоткрытые, номера включают обе конечные границы, серия сравнивается явно. Затем ORDER BY определяет ранг `(priority DESC, rev_order DESC)`; id используется только для воспроизводимого перечисления. Java сохраняет все строки с первой парой ранга, не выбирает победителя по случайному порядку ResultSet.

После `j02-ambiguity.sql` результат для SEN — AMBIGUOUS [SEN-B, SEN-X]. LIMIT 1 замаскировал бы конфликт. Если приоритет одного повысить, именно это явное правило разрешит выбор. Сортировка строковых меток A/B/C не заменяет rev_order и не гарантирует правильный порядок иной схемы ревизий.

Одна транзакция REPEATABLE READ даёт согласованный контекст чтения при нескольких запросах проверки идентичности и кандидатов. Она не превращает решение в долговечный baseline: после commit рабочие правила и состояния могут измениться. Для принятого исторического выбора нужен отдельный сохраняемый результат, как в J03.

Эталон выдаёт статус и победителей, но не все причины отсева. Расширенный explain-report из задания требует дополнительного кода. Также здесь нет опций, проверки конструкции, совместимости, производственной готовности или авторизации. Самооценка должна разделять эти вопросы и собственно выбор ревизии.
