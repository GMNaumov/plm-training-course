# J12. Разбор потоковой выгрузки

[К заданию](../exercises/j12-java-export/README.md) · [К эталонам](README.md) · [Исходник](java/StreamingExport.java)

После reset `docker compose run --rm java practice/solutions/java/StreamingExport.java OLD 100` создаёт `/artifacts/java-export.tsv`: 900 строк данных и заголовок. На хосте это practice/output/java-export.tsv. Запуск NEW 100 fail сохраняет прежний файл и удаляет временный.

Сервис подтверждает существование sealed snapshot и ограничивает copies. SQL имеет полный стабильный ORDER BY `(copy,path)`, а клиент читает ResultSet потоково. Fetch size 64 работает совместно с autoCommit=false; REPEATABLE READ фиксирует контекст чтения. Серверная сортировка остаётся отдельной затратой, ограничение клиентской памяти её не отменяет.

BufferedWriter сразу пишет данные в уникальный временный файл на том же томе. Escape задаёт простой явный TSV-контракт: обратная косая черта, TAB, CR/LF представлены последовательностями внутри ячейки. Метод не загружает весь отчёт в коллекцию. Число строк считается по реально прочитанным записям.

После закрытия ResultSet, writer и commit выполняется ATOMIC_MOVE с заменой итогового файла. При невозможности атомарного переноса выводится ошибка, гарантия не ослабляется скрытым fallback. finally удаляет остаток `.part`. Сбой на третьей строке происходит до публикации, поэтому старый отчёт остаётся целиком доступен.

Файл и БД не имеют общей распределённой транзакции. Здесь источник неизменяемый и публикация только файловая; для долговечного реестра публикаций потребуется отдельный восстанавливаемый протокол. Atomic rename не является обещанием fsync или защиты от отключения питания. Два конкурентных процесса публикуют целые файлы, последний заменяет предыдущий; отдельные идентичности отчётов — дальнейшее расширение.

Зерно `(copy,path)` не позволяет суммировать все assembly и part как одинаковый материальный расход. Copies — детерминированная нагрузка, не реальные серийные изделия. Неполные права и RLS не моделируются, поэтому перенос отчёта на реальный PLM требует явной границы видимости и полноты.
