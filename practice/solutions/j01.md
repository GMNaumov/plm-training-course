# J01. Разбор точных количеств

[К заданию](../exercises/j01-java-quantities/README.md) · [К эталонам](README.md) · [Исходник](java/QuantityService.java)

После reset выполните `docker compose run --rm java practice/solutions/java/QuantityService.java`. Получатся семь строк: M1/M2 KNOWN 1.25; M3 UNKNOWN; M4/M5/M7 INVALID; M6 DIMENSION_MISMATCH. Значение отсутствует у всех статусов, кроме KNOWN.

Метод сначала проверяет NULL, затем размерность, затем грамматику числа и положительность. Так неизвестное не превращается в ноль, а известная длина не выдаётся за массу. Конструктор BigDecimal получает строку, множитель тоже читается через getBigDecimal; double не появляется даже на промежуточном шаге. Умножение выполняется точно, stripTrailingZeros относится только к выводу.

Готовый Lab.positive ограничивает вход 80 символами и обычной десятичной записью. Поэтому INVALID для `1e3` — решение контракта, а не ограничение BigDecimal. Аналогично нулевая масса в этом упражнении недопустима по договору; это не универсальное правило всех измерений. Множитель берётся из доверенного учебного справочника; при расширении на внешнюю НСИ нужно отдельно защищать его конечность и размерность.

LEFT JOIN сохраняет строку измерения при проблеме справочника; замена на INNER JOIN сократила бы число строк и могла скрыть причину. Учебный FK не позволяет текущим данным иметь неизвестную unit, но при миграции и неполных правах одного FK недостаточно для полноты отчёта.

Повторный запуск ничего не изменяет. Суммировать M1 и M2 как массу двух разных компонентов нельзя без идентичностей и базы количества. Оцените своё решение по сохранности всех семи строк, точности пересчёта и объяснению каждого отказа.
