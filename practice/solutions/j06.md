# J06. Разбор конкурентного inbox

[К заданию](../exercises/j06-java-consumer/README.md) · [К эталонам](README.md) · [Исходник](java/OrderedConsumer.java)

После reset выполните последовательность задания с путём `practice/solutions/java/OrderedConsumer.java`: APPLIED, REPLAY, конфликт payload, gap, fail, затем успешная версия 2. Итог — одна проекция версии 2 и две квитанции APPLIED.

Первым резервируется **глобальный** eventId уникальным INSERT. Это важно и при разных агрегатах: блокировка только aggregate_id не защищает один eventId от двух договоров. Незавершённый конкурентный INSERT ждёт, затем при READ COMMITTED отдельный SELECT видит его зафиксированный результат. PENDING никогда не коммитится по нормальному протоколу.

Строка java_target материализуется через ON CONFLICT DO NOTHING перед FOR UPDATE. Так защищён первый приём агрегата, которого ещё нет. SELECT FOR UPDATE отсутствующей строки сам по себе ничего не резервирует. После блокировки проверяется current+1, обновляется payload, затем квитанция становится APPLIED. Всё фиксируется вместе.

При fail откатываются и строка первого агрегата, и резерв eventId, и эффект. Повтор с тем же договором может примениться. При повторе уже применённого eventId версия агрегата заново не проверяется: историческая квитанция остаётся верной и после следующих событий. Новый eventId со старой версией не является replay и отвергается.

Для разных агрегатов общая блокировка таблиц L13 не используется. Таблицы по-прежнему имеют обычные служебные блокировки PostgreSQL; утверждение относится к отсутствию явной сериализации всех потребителей. Порядок событий не гарантируется транспортом: версия 2 до 1 получает gap, буфера в эталоне нет.

Payload сравнивается точно как String; канонизация JSON, schema evolution и настоящая сеть не реализованы. Называть эту модель exactly-once доставкой неверно. Она обеспечивает один локальный эффект для принятого eventId при выполнении договора всеми писателями и общей атомарности эффекта с inbox.
