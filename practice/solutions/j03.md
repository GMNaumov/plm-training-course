# J03. Разбор полного снимка

[К заданию](../exercises/j03-java-snapshot/README.md) · [К эталонам](README.md) · [Исходник](java/BaselineSnapshot.java) · [Ограничения SQL](../java/advanced/schema.sql)

После reset: `docker compose run --rm java practice/solutions/java/BaselineSnapshot.java SNAP-1`. Результат CAPTURED=9; сумма root_quantity для BOLT — 12. o35 не включён по явному контракту BASE. Итоговые таблицы не являются view поверх изменяемой occurrence.

Чтение начинается со всех обязательных occurrence, а не с существующих строк baseline. LEFT JOIN оставляет потерянный выбор видимым; Java проверяет выбранную идентичность и точное положительное количество до построения результата. Готовый base_tree для этой проверки непригоден: INNER JOIN способен скрыть пропавшую строку.

Обход хранит набор предков текущей ветви. После выхода ревизия удаляется из набора, поэтому одна подструктура может законно появиться в нескольких местах. Глобальное visited ошибочно свернуло бы повторные использования. Полный path служит идентичностью строки раскрытия, local_quantity описывает отношение, root_quantity — произведение на корневой модуль. Ограничения 128 уровней и 10000 путей дают объяснимый отказ вместо неконтролируемого раскрытия.

В REPEATABLE READ читаются и связи, и выборы, и контекст. Заголовок, строки batch и seal фиксируются одной транзакцией. Сначала строки могут вставляться в незапечатанный заголовок; триггер берёт его FOR UPDATE. Seal допускается только как переход false→true без изменения остальных полей. После seal запрещены INSERT строк, UPDATE/DELETE данных. Это не аудит против владельца: TRUNCATE, выключение триггеров и DDL должны регулироваться отдельными полномочиями.

`j03-missing.sql` даёт MISSING_SELECTION:h10; `j03-wrong-item.sql` — WRONG_ITEM:h10. Ни в одном случае не остаётся нового заголовка. Цикл и NaN тоже приводят к rollback. Повтор id вызывает UNIQUE-конфликт. Старый снимок после изменения h10 с 6 на 7 сохраняет 6; новый показывает 7. Исходная BASE-01 сама этого не гарантирует, потому что quantity продолжает жить в occurrence.

Эталон сохраняет контекст как данные и правило snapshot-v1, не проверяя заново сегодняшнюю допустимость исторических ревизий. Он поддерживает базовое исполнение и счётные количества. Отдельная модель вариантов и массовых норм требует явного нового контракта; её нельзя получить удалением неудобных строк JOIN.
