# J05. Разбор команды внедрения

[К заданию](../exercises/j05-java-change/README.md) · [К эталонам](README.md) · [Исходник](java/ChangeRelease.java)

Первый вызов после reset отказывает PENDING_ACTIONS. Затем выполните j05-ready.sql и команды задания, заменив путь на `practice/solutions/java/ChangeRelease.java`. Вызов с fail откатывается; без fail возвращает IMPLEMENTED; точный повтор — REPLAY:IMPLEMENTED.

UNIQUE-резервирование commandId решает гонку ещё не существующей команды. В READ COMMITTED следующий SELECT после конфликта видит победивший договор. Квитанция хранит changeId, expectedVersion и предметный результат. После rollback резерва нет и корректный повтор может примениться. При другом expectedVersion под тем же commandId команда конфликтует, а не становится новой попыткой.

Блокировка change_order задаёт область агрегата. Используется FOR NO KEY UPDATE: FK команды уже удерживает KEY SHARE, а два конкурентных FOR UPDATE создали бы deadlock при усилении. NO KEY UPDATE совместим с KEY SHARE и сериализует обновления неключевых полей. Проверка pending защищена только если писатели change_action сначала берут ту же блокировку; j05-ready.sql демонстрирует этот договор. Прямой INSERT в change_action вне протокола может нарушить гарантию — приложение и права БД нужно проектировать совместно. Условный UPDATE и проверка affected rows сохраняют явный CAS, даже при удерживаемой блокировке.

Состояние implemented, lock_version=1, событие CHANGE:CH-1:1, строка доставки и результат IMPLEMENTED принадлежат одной локальной транзакции. Сбой после INSERT outbox не оставляет события без изменения и наоборот. Вызов получателя в эту транзакцию не входит.

Два commandId с ожидаемой версией 0: один успешен, второй STALE_VERSION. Два одинаковых commandId: применение и replay. Исключение во время commit может означать неизвестный клиенту результат; проверяйте квитанцию новым соединением и повторяйте тот же договор. Lab.rollback не делает неопределённый ответ commit доказанным откатом.

Поток CHANGE независим от MBOM. Протокол содержит один переход и не реализует полный workflow, согласование ролей, отмену и компенсацию внешних эффектов. Сравнивайте своё решение по атомарности и предметному результату, а не только наличию аннотации transactional в иной реализации.
