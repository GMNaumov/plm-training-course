# J07. Доставщик outbox: аренда, повтор и потерянный ответ

[Все задания](../README.md) · [Java-ветка](../../java/advanced/README.md) · [Теория](../../../course/17-apis-and-enterprise-integration/theory.md) · [Глоссарий](../../../references/glossary.md)

## Задача и предварительные условия

Прочитайте L13, J05 и протокол J06. Нужны SELECT FOR UPDATE SKIP LOCKED, UUID и границы транзакций. Создайте доставщик с короткой арендой работы и защитой от запоздалого подтверждения прежнего работника.

После reset в `java_outbox` два события версии 1 для независимых агрегатов; в `java_delivery` — их состояния доставки. Реализуйте [OutboxWorker.java](../../java/advanced/OutboxWorker.java). Он вызывает соседний OrderedConsumer. Чтобы проходить J07 независимо от J06, после попытки J07 скопируйте готовый [OrderedConsumer.java](../../solutions/java/OrderedConsumer.java) в свой рабочий каталог рядом с OutboxWorker и Lab; собственную попытку J06 предварительно сохраните. Это инфраструктура получателя, не скрытое требование закончить J06.

## Протокол

1. В короткой транзакции выберите одну неподтверждённую доставку с истёкшей либо отсутствующей арендой. SKIP LOCKED позволяет другим работникам брать другие строки. Это очередь, не согласованный аналитический запрос.
2. Запишите новый token UUID, срок по часам БД `clock_timestamp()+10 seconds` и увеличьте attempts. Зафиксируйте claim **до** вызова получателя.
3. Вызовите получателя отдельной транзакцией. Блокировка отправителя во время I/O уже снята.
4. Подтвердите строку только при совпадении eventId, token, незавершённого состояния и ещё действующей аренды. Старый работник не вправе затереть более новую попытку.
5. При отсутствии работы верните IDLE. При отказе получателя аренда остаётся до истечения, затем событие можно взять снова. Отдельного бесконечного retry-loop в эталоне нет.

```text
docker compose run --rm java practice/java/advanced/OutboxWorker.java crash
```

## Основной отказной сценарий

После reset первым выбирается EVT-1. Получатель печатает APPLIED, затем процесс падает с CRASH_AFTER_RECEIVER_COMMIT. В java_target уже есть версия 1, java_event содержит APPLIED, но java_delivery.delivered=false и attempts=1. Это ожидаемый разрыв двух транзакций.

Сразу повторите без crash: может быть взято второе событие J-EVT-2, пока EVT-1 арендовано. После истечения десятисекундной аренды повторите снова. Получатель вернёт REPLAY:APPLIED, отправитель отметит доставку, attempts EVT-1 станет 2. Повторяйте по одному вызову, пока не получите IDLE; порядок наблюдений объясняйте состоянием БД, а не ожиданием ровно одного процесса.

```text
docker compose run --rm java practice/java/advanced/OutboxWorker.java
```

## Конкурентность и самостоятельная оценка

После нового reset запустите два доставщика одновременно в двух терминалах с одним Compose-именем. Они должны подтвердить оба независимых события без двойного эффекта. В своей реализации сохраните Claim, дождитесь истечения аренды, выдайте новую и попробуйте acknowledge старого token: ожидается false. Точное время выполнения Java не является доказательством отсутствия гонки.

Вы должны показать три отдельные фиксации: claim отправителя, эффект и inbox получателя, ack отправителя. Транспорт представлен вызовом Java с другим соединением; реального брокера или HTTP здесь нет. Потеря результата commit получателя разрешается повтором того же eventId.

## Углубление

Спроектируйте backoff и отдельную очередь исключений с ограничением попыток. Затем запрет выдачи версии N+1 до подтверждения N для одного агрегата: текущая очередь такого порядка не гарантирует, получатель отклоняет gap. Затем добавьте длительный обработчик и продление аренды с проверкой token. Не называйте UUID численно монотонным fencing counter: здесь это уникальный токен владения для условного UPDATE.
