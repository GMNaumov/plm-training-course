# J02. Объяснимый решатель ревизий

[Все задания](../README.md) · [Java-ветка и запуск](../../java/advanced/README.md) · [Теория](../../../course/09-revision-configuration/theory.md) · [Глоссарий](../../../references/glossary.md)

## Задача и предварительные условия

Прочитайте тему 09 и L06. Нужны JDBC, LocalDate, неизменяемые записи и сортировка. Реализуйте разрешение одной идентичности изделия в контексте даты, серии и номера. Решатель должен отличать отсутствие кандидатов от неоднозначного выбора.

Перед сценарием выполните reset. Используются `item` и `revision`. Выбор здесь динамический; `occurrence.fixed_revision` и исторический BASE-01 не переопределяются. Сервис не принимает производственного решения о пригодности изделия.

## Контракт и шаги

1. В [RevisionResolver.java](../../java/advanced/RevisionResolver.java) проверьте полноту контекста: дата, непустая серия, положительный номер.
2. Неизвестную идентичность изделия диагностируйте отдельно от UNRESOLVED известного изделия.
3. Допускайте только released; интервал дат `[valid_from, valid_to)`, серийный диапазон — с включёнными границами и только в указанной серии. NULL верхней границы означает отсутствие ограничения.
4. Среди допущенных выберите максимальную пару `(priority, rev_order)`. Не используйте строковую метку ревизии как номер и не снимайте ничью сортировкой по id.
5. Верните Decision с RESOLVED и одним id, UNRESOLVED и пустым списком либо AMBIGUOUS со всеми равноприоритетными победителями. Список неизменяемый, порядок вывода стабильный.

```text
docker compose run --rm java practice/java/advanced/RevisionResolver.java HO 2026-06-01 DM 100
docker compose run --rm java practice/java/advanced/RevisionResolver.java HO 2026-07-01 DM 101
docker compose run --rm java practice/java/advanced/RevisionResolver.java SEN 2026-07-01 DM 100
```

## Границы и ожидаемые результаты

Первые три результата: HO-A, HO-B и SEN-B. Для HO на `2026-07-01/DM/100` остаётся HO-A; HO-B ещё не допускается по номеру. Для SEN на `2026-06-30` выбирается SEN-A, а на `2026-07-01` — SEN-B. Серия OTHER даёт UNRESOLVED. HO-C не выбирается несмотря на больший rev_order.

После отдельного reset выполните:

```text
docker compose exec -T db psql -X -U plm_owner -d plm -v ON_ERROR_STOP=1 -f /workspace/practice/java/advanced/j02-ambiguity.sql
docker compose run --rm java practice/java/advanced/RevisionResolver.java SEN 2026-07-01 DM 100
```

Ожидается AMBIGUOUS с SEN-B и SEN-X. Затем в своей копии набора поднимите priority одного кандидата: неоднозначность должна исчезнуть по явному правилу. Верните reset перед следующей независимой попыткой.

## Самостоятельная оценка и углубление

Объясните допуск каждого кандидата отдельно от его ранга. Предъявите пограничные даты и номера, неизвестное изделие и два победителя. Не выдавайте AMBIGUOUS за «первую строку» и не обещайте воспроизведение старого выбора по изменившимся правилам.

Дополнительно верните причины отсева каждой ревизии; затем сохраните версию правил и принятый контекст; затем объедините решатель с проверкой полноты опций, сохранив отдельные состояния логики и конструкции. Эти расширения не входят в готовый код; базовый контракт выбирает одну идентичность без опций и проверки совместимости.
