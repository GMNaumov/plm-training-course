# J10. Двухвременная история и исправление факта

[Все задания](../README.md) · [Java-ветка](../../java/advanced/README.md) · [Теория](../../../course/15-physical-product-lifecycle/theory.md) · [Глоссарий](../../../references/glossary.md)

## Задача и предварительные условия

Прочитайте L12 и его ограничение: по текущему effective_to и recorded_at нельзя восстановить утраченную дату знания. Нужны OffsetDateTime, SQL-интервалы и JDBC. Реализуйте чтение по двум временным осям и контролируемую новую редакцию факта.

После reset `java_fact` содержит независимый набор истории одной позиции DM-100/30. F1/1: S-001 считался установленным бессрочно; 12 августа стало известно о демонтаже 10 августа. F1/2 сохраняет уточнённый интервал. F2/1 — поздняя регистрация S-002 с 10 августа. Это дополнительная модель, а не реконструкция знания по исходной installation.

## Чтение и исправление

В [TemporalHistory.java](../../java/advanced/TemporalHistory.java) заполните `at` и `correct`:

1. Для at выберите факт, интервал действия которого содержит effective, а интервал знания — known. Оба интервала `[from,to)`. Условие только по recorded_at недостаточно.
2. Отсутствие результата обозначьте NO_KNOWN_FACT, не «позиция достоверно пуста». Две одновременно выбранные установки в этом одно-позиционном наборе — CONTRADICTORY_POSITION_HISTORY.
3. Исправление принимает factId, ожидаемую edition, момент новой регистрации и уточнённое effective_to. Блокируйте текущую редакцию, проверьте границы, закройте **интервал знания**, добавьте новую редакцию.
4. Прежние effective_from/effective_to и ребёнок старой редакции остаются неизменными. Коррекция с устаревшей edition отказывает. Закрытие и добавление новой редакции выполняются одной транзакцией.

```text
docker compose run --rm java practice/java/advanced/TemporalHistory.java at 2026-08-11T00:00:00Z 2026-08-11T00:00:00Z
docker compose run --rm java practice/java/advanced/TemporalHistory.java at 2026-08-11T00:00:00Z 2026-08-13T00:00:00Z
docker compose run --rm java practice/java/advanced/TemporalHistory.java at 2026-08-10T00:00:00Z 2026-08-12T00:00:00Z
```

## Ожидаемые результаты

Первый запрос: F1/1 S-001. Второй: F2/1 S-002. Третий, ровно на обеих границах, тоже F2/1 S-002. Физический момент один, знания о нём разные. Историческое утверждение не стирается сегодняшним исправлением.

После отдельного reset задайте коррекцию:

```text
docker compose run --rm java practice/java/advanced/TemporalHistory.java correct F1 2 2026-09-01T00:00:00Z 2026-08-09T00:00:00Z
docker compose run --rm java practice/java/advanced/TemporalHistory.java at 2026-08-09T12:00:00Z 2026-08-31T00:00:00Z
docker compose run --rm java practice/java/advanced/TemporalHistory.java at 2026-08-09T12:00:00Z 2026-09-02T00:00:00Z
```

Ожидаются CORRECTED:3, F1/2 S-001, NO_KNOWN_FACT. Последнее означает пробел известной истории, а не автоматически подтверждённый демонтаж с отсутствием компонента. Повтор коррекции с edition=2 — STALE_EDITION. Нельзя поставить knownAt раньше или ровно в known_from текущей редакции.

## Самооценка и углубление

Проверьте три строки F1 после коррекции и сохранность старого интервала. Два конкурентных исправления одной текущей редакции должны дать одну новую редакцию и один stale. В разных часовых смещениях один instant должен давать одинаковую выборку.

Базовое correct исправляет один факт и может создать предметное противоречие с F2, если продлить F1 дальше установки S-002; at обязано это обнаружить. Сервис не заявляет полной межфактной целостности истории. Дополнительно спроектируйте коррекцию всей позиции под общей блокировкой; затем историю основания отмены; затем независимые роли регистрации и инженерного принятия. Времена знания в fixture — управляемые синтетические данные, не журнал системных часов.
