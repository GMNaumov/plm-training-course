# J12. Потоковая выгрузка и атомарная публикация отчёта

[Все задания](../README.md) · [Java-ветка](../../java/advanced/README.md) · [Теория аналитики](../../../course/19-traceability-and-analytics/theory.md) · [Глоссарий](../../../references/glossary.md)

## Задача и предварительные условия

Прочитайте тему 19 и контракт J03. Нужны JDBC cursor, BufferedWriter, REPEATABLE READ и операции файловой системы. Реализуйте выгрузку, которая не накапливает все строки в heap и не публикует частичный отчёт после отказа.

После reset готовый OLD содержит девять путей. Для нагрузки SQL детерминированно размножает строки `generate_series(1,copies)`; это синтетические копии анализа, а не физические изделия. Зерно отчёта — `(copy, path)`, количество относится к одному корневому ДМ-01. Суммировать количество по всем строкам, включая сборки и их детали, как одно потребление запрещено смыслом модели.

## Контракт и реализация

В [StreamingExport.java](../../java/advanced/StreamingExport.java) заполните `write`:

1. Разрешите 1…10000 копий и только существующий sealed snapshot. Неверное имя — отказ, а не пустой отчёт.
2. Читайте одним упорядоченным SQL по copy и path внутри REPEATABLE READ с autoCommit=false. Установите fetchSize=64; одна настройка fetchSize при autoCommit=true не обеспечивает нужный cursor в pgJDBC.
3. Пишите строки сразу в UTF-8 BufferedWriter, без List всех результатов. TSV имеет заголовок и пять столбцов: copy, path, revision, quantity, unit. Escape TAB, переводы строк и обратную косую черту; переводов строк внутри ячейки файла быть не должно.
4. Создавайте уникальный временный `.part` только в `/artifacts`, закрывайте writer и транзакцию до публикации. Перенесите файл атомарно в `java-export.tsv` на том же томе.
5. При fail после третьей строки удалите временный файл; старый итоговый отчёт сохраните. Если ATOMIC_MOVE не поддерживается, сообщите отказ, не обещайте ту же гарантию через обычное копирование.

```text
docker compose run --rm java practice/java/advanced/StreamingExport.java OLD 100
docker compose run --rm java practice/java/advanced/StreamingExport.java NEW 100 fail
```

## Ожидаемые результаты и самооценка

Первый запуск: EXPORTED=900, в `practice/output/java-export.tsv` 901 строка с заголовком. Второй падает, прежний файл остаётся побайтно тем же и `.part` не остаётся. Откройте файл редактором и проверьте порядок строк, UTF-8 и количественные поля. После нового reset исходный OLD по-прежнему доступен; выходной файл reset не удаляет.

Для OLD 10000 ожидаются 90000 строк данных. Измерьте время и память в контексте своей машины, не объявляя результат характеристикой коммерческого PLM. SQL-сортировка может требовать память или временные файлы на сервере даже при потоковом чтении клиента. Текущий statement_timeout=10s в Lab — учебная граница; тайм-аут является отказом, а не разрешением публиковать усечённый отчёт.

Одновременно два процесса публикуют только целые файлы, но последний успешный rename заменяет предыдущий отчёт. Это не сериализация бизнес-заданий. Для независимых публикаций потребуется отдельное имя/идентичность отчёта. Atomic rename не обещает устойчивости к отключению питания без отдельной модели fsync и носителя.

## Углубление

Добавьте манифест отчёта с snapshotId, версией запроса, числом строк и хешем файла. Затем спроектируйте возобновление по составному ключу без OFFSET и без смешения разных снимков. Затем введите область видимости и отдельный признак неполного отчёта; RLS здесь не моделируется, владелец видит учебный набор целиком. Это предметная практика темы 19, не экзамен и не задание итогового проекта.
