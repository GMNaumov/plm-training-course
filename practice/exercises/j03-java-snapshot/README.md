# J03. Полный снимок состава и атомарное запечатывание

[Все задания](../README.md) · [Java-ветка и запуск](../../java/advanced/README.md) · [Теория EBOM](../../../course/08-engineering-bom/theory.md) · [Глоссарий](../../../references/glossary.md)

## Задача и предварительные условия

Прочитайте L05 и разбор границ BASE-01 в теме 09. Нужны рекурсивный обход графа, JDBC batch и изоляция транзакций. Постройте точный снимок ДМ-01, сохраняющий не только выбранные ревизии, но и значимые связи, пути и количества.

После reset используйте BASE-01 и DM-A. Контракт охватывает **базовое исполнение**: все достижимые occurrence без option_code обязательны; o35 исключён явно. Не пытайтесь по отсутствию строки baseline угадать необязательность. Поддерживаются количества счётной размерности; смесь массовой нормы и количества изделий требует другой модели.

## Что сохранить и реализовать

В [BaselineSnapshot.java](../../java/advanced/BaselineSnapshot.java) реализуйте `capture` и `walk`:

1. Прочитайте occurrence и выборы в одном REPEATABLE READ. LEFT JOIN должен оставить видимой потерю обязательного выбора. Сверьте child_item выбранной ревизии.
2. Обходите от DM-A. Путь состоит из id вхождений через `/`. Множество предков относится к текущей ветви: повторное использование допустимо, цикл — отказ. Введите предел глубины 128 и числа путей 10000.
3. Сохраните локальное количество, произведение на корневой модуль, единицу, родителя и выбранную ревизию. Используйте BigDecimal и отклоняйте NaN/Infinity и неположительные количества до вычисления.
4. Проверьте одинаковый context исходных строк, сохраните его вместе с `snapshot-v1` и корневой ревизией. Снимок объясняет исторический выбор, а не повторно применяет сегодняшнюю применяемость.
5. Создайте заголовок, пакетно вставьте строки и выполните seal одной транзакцией. Любая ошибка оставляет ноль строк нового снимка.

```text
docker compose run --rm java practice/java/advanced/BaselineSnapshot.java SNAP-1
```

## Нормальный сценарий

Ожидаются `CAPTURED=9`, девять путей SNAP-1 и 12 ea крепежа по трём путям 6+4+2. Снимок не содержит корень отдельной строкой. После фиксации измените рабочее количество h10 с 6 на 7 через psql: SNAP-1 сохраняет 6 и итог 12; новый SNAP-2 содержит 7 и итог 13. Это изменение учебных рабочих данных, не новая выпущенная конструкция.

```sql
SELECT path,local_quantity,root_quantity FROM lab.java_snapshot_line
WHERE snapshot_id='SNAP-1' ORDER BY path;
UPDATE lab.occurrence SET quantity=7 WHERE id='h10';
```

## Отказы и самооценка

После отдельных reset загрузите `j03-missing.sql` и `j03-wrong-item.sql` из каталога `practice/java/advanced` командой psql с `-f`, затем повторите capture с новым id. Ожидаются соответственно MISSING_SELECTION:h10 и WRONG_ITEM:h10, без заголовка и строк результата. Повтор имени существующего снимка даёт конфликт, не перезаписывает историю.

Попытки UPDATE/DELETE строк или INSERT новой строки в запечатанный снимок должны завершаться ошибкой триггера. Это защита протокола, а не от владельца, отключающего триггеры. Для собственного сценария цикла добавьте допустимое по FK вхождение обратно в DM-A и его baseline-выбор; ожидайте CYCLE и rollback. Удалите изменения через reset.

Вы можете объяснить, почему `base_tree` не используется как источник: готовый INNER JOIN способен спрятать отсутствие обязательного выбора. Согласованное чтение не замораживает инженерное решение навсегда; фиксация значимых отношений делает это в границах данного контракта.

## Дополнительное исследование

Сохраните отдельно нормализованные определения связей и раскрытые пути; затем добавьте явно выбранное исполнение с опциями; затем спроектируйте права создателя и читателя снимка. Не выдавайте расширенный контракт за уже реализованный.
