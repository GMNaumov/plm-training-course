# Администрирование типов, атрибутов, связей и правил

[К теме «Администрирование, модель доступа и расширение системы»](../README.md)

## Основная идея

Расширение схемы начинается с предметного смысла: какой факт хранится, кто его задаёт и когда он обязателен. Создание поля без этих решений переносит неопределённость в данные.

## Элементы конфигурации

Для атрибута задают тип, кратность, единицу, источник и правила изменения. Для связи — типы концов, направление и обязательность. Для типа объекта — наследуемые свойства и отличающие правила. Классификационный признак не обязательно требует нового системного типа.

## Эволюция модели

Новый обязательный атрибут затрагивает существующие записи, импорт, API и отчёты. Нужна политика заполнения старых данных. Удаление значения справочника может нарушить историю: часто прекращают новый выбор, сохраняя старые ссылки. Настройка интерфейса проверяется отдельно от серверных ограничений.

## Новый тип или новый класс

Новый системный тип обоснован, когда отличается поведение: жизненный цикл, полномочия, допустимые отношения или обязательные правила. Новый класс обоснован, когда меняется предметное описание для поиска. Например, разные виды датчиков могут иметь общую механику выпуска, но разные классификационные признаки. Создание отдельного типа на каждый диапазон измерения перегружает схему.

## Переход существующих данных

При введении обязательного признака старые записи могут оставаться исторически корректными, но неполными для нового выпуска. Возможна политика проверки по состоянию: признак обязателен при следующем пересмотре, а прошлый выпуск сохраняется. Другая политика требует управляемого дополнения всей области. Выбор фиксирует владелец модели.

Значение по умолчанию безопасно только при известном смысле. Автоматическое присвоение материала всем старым деталям создаст заполненные, но ложные данные. Для неизвестного факта нужен явный статус и процесс уточнения.
