# Сервисная модель, API и контракты данных

[К теме «API, расширения и интеграция предприятия»](../README.md)

## Основная идея

Сервисный контракт описывает действие над предметной моделью. Он включает идентификаторы, версии, единицы, обязательность полей, предусловия и различимые результаты ошибок.

## Семантика операции

Создание, изменение и выпуск имеют разные полномочия. Для изменения полезна ожидаемая версия: несовпадение сообщает о конкурентном редактировании. Для списочных методов нужны правила пагинации и стабильности среза; несколько страниц текущих данных не обязательно образуют один исторический снимок.

## Пример

Получатель получает количество 10 без единицы и контекста. Синтаксис корректен, предметный смысл неизвестен. Совместимость контрактов требует не только сохранения поля, но и неизменности его значения. Документация конкретного API и авторизация будут выбраны на этапе практики; здесь нет вымышленных конечных точек или обещаний поддержки определённых продуктов.

## Предусловие изменения

Запрос может содержать ожидаемую версию, на основе которой пользователь подготовил действие. Если текущая версия иная, сервис сообщает конфликт. Такой контракт защищает от незаметной потери чужих изменений, но не решает инженерный конфликт автоматически: пользователю нужно сопоставить различия.

Частичное обновление также требует семантики отсутствующих полей. Не переданное поле может означать «сохранить», а явно пустое — «очистить», если это разрешено. Смешение этих случаев приводит к повреждению сведений при совместном использовании клиентов разных версий.

## Стабильность выборки

При получении данных страницами задаются порядок, граница среза и правила появления новых объектов. Иначе одна позиция может повториться или исчезнуть между страницами. Для конфигурационного отчёта особенно важно сохранить согласованный контекст. Версия контракта отражает не только структуру полей, но и изменение их смысла, обязательности и правил ошибок.
