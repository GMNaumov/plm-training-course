# Связи требований, конструкций, производства и экземпляров

[К теме «Сквозная прослеживаемость и инженерная аналитика»](../README.md)

## Основная идея

Граф прослеживаемости объединяет предметные области, сохраняя семантику каждой связи. Он может храниться реляционно; наличие графовых запросов не обязывает выбирать специальную графовую БД.

## Контекст рёбер

У отношения могут быть версия, направление, роль, область действия и источник. Связь испытания с ревизией отличается от связи с физическим экземпляром: обе могут быть необходимы. Временная установка требует интервала, а происхождение партии — события преобразования.

## Пример

Путь «требование → узел → производственная операция → протокол» полезен только если определено значение каждого перехода. Протокол операции может подтверждать отдельную характеристику, но не всё требование узла. Показ существующего пути без объяснения ролей создаёт ложное представление о полноте доказательств.

## Правило обхода как часть вопроса

Для каждого перехода задаются роль, направление и ограничения контекста. Связь «подтверждает» обычно читается от свидетельства к проверяемому условию; для отчёта покрытия может понадобиться обратный поиск. Направление вычисления не меняет смысл самого отношения.

Если два пути ведут к одному экземпляру, их можно объединить в итоговом перечне, сохранив разные причины включения. Это полезно, когда объект затронут и проблемой материала, и изменением программной конфигурации.

## Происхождение связей

Связь может быть создана автором, импортирована или вычислена по правилу. Эти источники имеют разную степень проверки. Автоматически предполагаемая связь не должна выглядеть принятым инженерным утверждением без основания. Для важных выводов сохраняют метод получения и результат рассмотрения. Так пользователь понимает, какие участки цифровой нити подтверждены, а где модель лишь указывает возможную зависимость.
